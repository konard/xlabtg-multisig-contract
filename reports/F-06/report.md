# F-06 — Срок действия заказа зависит от `now()`

## Краткое описание

TON Multisig V1 использует TVM `now()` для проверки `query_id`/expiry и cleanup. Это стандартный источник времени блока. Производитель блока имеет ограниченную свободу выбора timestamp, однако исходный материал не показывает сценарий, в котором эта свобода приводит к обходу подписи, повторному выполнению или потере средств.

## Затронутый компонент

- Репозиторий: `https://github.com/xlabtg/multisig-contract`
- Commit: `ef8633e642f247761c7c11e62cc437fa01a42705`
- Файл: `multisig-code.fc`
- Функция: `recv_external`
- Строки: 153–162, 183–200

## Предпосылки

- Заказ находится очень близко к границе expiry.
- Block producer выбирает допустимый timestamp, смещающий момент принятия/отклонения около границы.

## Корневая причина

`bound = now() << 32` участвует в проверке просроченности, минимального времени жизни solo proposal и cleanup. Другого доверенного on-chain clock у контракта нет.

## Шаги воспроизведения

1. В локальном emulator создать запрос с `query_id`, близким к timestamp boundary.
2. Выполнить его при двух допустимых значениях block time по разные стороны границы.
3. Наблюдать ожидаемое различие accept/reject по exit code 33/41.

Это демонстрирует зависимость от времени, но не security vulnerability. Исполняемый PoC не приложен; live mainnet/testnet не использовались.

## Ожидаемый и фактический результат

Ожидание: expiry следует timestamp блока.

Фактически код именно так и работает. Нарушение документированного/безопасностного свойства не выявлено.

## Влияние

Не доказано. Возможна только обычная пограничная неопределённость времени включения транзакции; replay protection и требование кворума сохраняются.

## Рекомендации

- не назначать критичные операции на точную границу expiry;
- учитывать запас времени в off-chain tooling;
- не менять контракт без конкретного exploit scenario.
