# F-01 — Владелец одного ключа может расходовать баланс на комиссии

## Краткое описание

В TON Multisig V1 внешний запрос с одной корректной подписью владельца принимается даже при недостигнутом пороге `k`. Контракт оплачивает вычисления и хранение незавершённого ордера из собственного баланса. Вредоносный владелец либо атакующий с одним скомпрометированным ключом может циклически создавать незавершаемые ордера и постепенно расходовать баланс на комиссии.

Это griefing, а не кража: средства не переводятся атакующему, и выполнить исходящие сообщения без `k` различных подписей нельзя.

## Затронутый компонент

- Репозиторий: `https://github.com/xlabtg/multisig-contract`
- Commit: `ef8633e642f247761c7c11e62cc437fa01a42705`
- Файл: `multisig-code.fc`
- Функции: `recv_external`, `update_pending_queries`
- Строки: 86–100, 130–133, 148–173, 183–200

## Предпосылки атаки

- `k >= 2`.
- Атакующий контролирует ровно один действующий ключ владельца.
- На контракте есть баланс для оплаты комиссий.

Анонимный пользователь без ключа не может вызвать поведение: корневая подпись проверяется до принятия сообщения.

## Корневая причина

On-chain voting намеренно оплачивается самим multisig:

- `set_gas_limit(100000)` принимает валидный запрос до достижения кворума;
- при `cnt < k` запрос записывается в `pending_queries`;
- после `commit()` состояние сохраняется даже без выполнения исходящих сообщений;
- завершающий cleanup выполняется после `accept_message()`.

## Шаги воспроизведения

Безопасный сценарий для локального TVM/emulator:

1. Развернуть V1 с `n > k >= 2` и пополнить только локальный баланс.
2. Одним ключом создать десять разных запросов с `query_id > now + 1 hour`, чтобы пройти exit code 41.
3. Отправить каждый запрос без со-подписей.
4. Убедиться, что каждый запрос сохранён активным, но исходящих сообщений нет.
5. Сравнить баланс до и после: он уменьшается на gas/storage fees.
6. После истечения запросов и освобождения per-owner flood slots повторить цикл.

Исполняемый PoC не приложен; live mainnet/testnet не использовались.

## Ожидаемый и фактический результат

Ожидание безопасности: один ключ при `k >= 2` не должен позволять неограниченно инициировать оплачиваемые кошельком операции.

Фактически один ключ может инициировать хранение и обработку запросов за счёт multisig. Лимит `flood <= 10` и минимальный час жизни ограничивают скорость, но после expiry цикл повторяется.

## Влияние

- постепенная потеря баланса на сетевых комиссиях;
- засорение `pending_queries`;
- дополнительный риск доступности, описанный отдельно в F-02.

Кворум не обходится, прямой кражи нет. Такое поведение уже публично признано известной проблемой в `ton-blockchain/ton#168` и частично смягчено текущими ограничениями.

## Рекомендации

- для новых кошельков использовать Multisig V2, где инициатор оплачивает создание предложения;
- в V1 ввести глобальный предел активных запросов и более строгий rate limit;
- считать компрометацию одного ключа инцидентом и мигрировать средства.

## Среда проверки

Статический анализ исходников на 2026-07-13 UTC. Локальная компиляция и emulator не запускались: `func`/`fift` в среде отсутствуют. Рекомендуется дополнительная проверка через `acton` и локальный TVM.
