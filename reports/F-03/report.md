# F-03 — Подпись заказа не содержит адрес контракта

## Краткое описание

Co-signature проверяется над хешем части внешнего сообщения, содержащей `wallet_id`, `query_id` и сообщения для отправки, но не адрес текущего multisig и не хеш набора владельцев. Поэтому одна и та же подпись криптографически подходит идентичному заказу в другом V1-контракте с тем же `wallet_id`, если соответствующий публичный ключ присутствует в обоих наборах владельцев.

Это не позволяет подделать отсутствующую подпись и само по себе не обходит порог `k`.

## Затронутый компонент

- Репозиторий: `https://github.com/xlabtg/multisig-contract`
- Commit: `ef8633e642f247761c7c11e62cc437fa01a42705`
- Файл: `multisig-code.fc`
- Функции: `check_signatures`, `recv_external`
- Строки: 31–53, 123–159

## Предпосылки атаки

- Существуют два multisig V1 с одинаковым `wallet_id`.
- Они разделяют хотя бы один публичный ключ владельца.
- В обоих контрактах воспроизводится byte-identical order с одинаковым `query_id` и payload.
- Атакующий получил валидную подпись этого владельца для заказа в первом контракте и способен сформировать валидно подписанный root envelope для второго.

## Корневая причина

В строке 137 вычисляется `slice_hash(in_msg)` после извлечения signature dictionary. Проверяемый preimage не включает адрес выполняющегося контракта или уникальный хеш конфигурации владельцев. Изоляция зависит только от корректно уникального `wallet_id`.

## Шаги воспроизведения

Безопасный локальный сценарий:

1. Развернуть два V1-контракта с одинаковым `wallet_id` и одним общим владельцем.
2. Создать в обоих одинаковые `query_id` и payload.
3. Подписать order preimage общим ключом для первого контракта.
4. Включить ту же co-signature в root envelope для второго контракта, подписанный другим допустимым владельцем второго контракта.
5. Проверить, что `check_signature` принимает повторно использованную co-signature.

Исполняемый PoC не приложен; live mainnet/testnet не использовались.

## Ожидаемый и фактический результат

Ожидание: подпись голосования должна быть domain-separated конкретным контрактом.

Фактически domain separation обеспечивается только операторски назначаемым `wallet_id`; при его повторном использовании подпись переносима.

## Влияние

В необычной ошибочной конфигурации голос владельца за идентичный заказ может быть учтён во втором кошельке без отдельного намерения подписать именно его. Кворум и валидность остальных подписей сохраняются; практический вред без дополнительного сценария не доказан.

## Рекомендации

- гарантировать уникальность `wallet_id` для каждого deployment;
- включить адрес контракта или хеш полной owner-конфигурации в подписываемый preimage;
- документировать domain-separation invariant в deployment tooling.
